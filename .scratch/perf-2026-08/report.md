# ng2 模拟器性能 / 体验走查报告（2026-08-13）

## 0. 先说结论（含一条对我自己前期判断的更正）

**这一轮最有价值的产出是四个功能缺陷，不是性能数字。**

走查中期我曾把「帖子详情慢拖 54% janky frames、版块列表只有 0.3%」当成头号性能问题，
并据此派了两条修复线。**这个判断是错的**——逐阶段拆帧之后发现，
`Janky frames` 在这台模拟器上不是可信指标（证据见 §2.3）。
改前/改后在**同一个帖子**上做严格对拍，性能改动**没有带来可测量的差异**（§4）。

真正站得住的收获：

| # | 缺陷 | 状态 |
|---|---|---|
| P0-1 | 冷启后开到第 4 个版块，之后所有版块（含已成功过的）永久变成「这个版块还没有主题」，只有杀进程能复位 | **已修，设备验证通过** |
| P0-2 | 反封锁链的凭证只放 `Cookie` 请求头，被 OkHttp 的 `BridgeInterceptor` 无条件替换 → 间歇性掉登录态 | **已修，设备上观察到改前/改后差异** |
| P1-4 | 正文图片的 `natural`/`failed` 是裸 state，FlashList 回收复用时新图会顶着上一张的比例、甚至上一张的「加载失败」画面 | 已修 |
| P1-5 | 版面镜像行的负数版块 ID 被当成无符号 32 位（`版面ID4286241377不存在`） | 已定位，修复见 §3.5 |

性能侧的诚实结论：**app 每帧自己花的 CPU 只有约 2ms，而这台模拟器每帧固定要 13.4ms
等 GPU 交换缓冲**——app 侧有巨大余量，这台设备上量不出 app 的渲染差异。
要判断真机手感，必须去真机上测（§5）。

## 1. 测什么、怎么测

### 被测对象

**release 包**，不是 dev client（dev 的 JS 开发模式会把帧数据搞脏）：

```bash
cd android && ANDROID_HOME=~/Library/Android/sdk ./gradlew :app:assembleRelease
adb install -r android/app/build/outputs/apk/release/app-release.apk
```

- 设备：`Pixel_8` AVD（`sdk_gphone16k_arm64`），1080×2400，density 420，**60Hz**
- GPU：**主机 GPU**（`GLES: Android Emulator OpenGL ES Translator (Apple M4), 4.1 Metal`），
  不是 SwiftShader；guest→host 走 `gltransport=pipe`
- 构建：Hermes 字节码（bundle 4.2MB），`minifyEnabled=false`，4 ABI 合包 121MB
  （production 走 aab 会按 ABI 拆，不是发布问题）

### 走查脚本

`scratchpad/perf.py` + `tour.py`，全自动无人值守：deeplink 进版块 → `uiautomator dump`
认页面状态并取行坐标点进主题 → 每屏跑**慢拖**（`input swipe` 800ms）与**快甩**（90ms）
两种滚动，每 5 帖加一轮横滑翻页 → 每个版块前 `am force-stop`（原因见 P0-1）。

**基线轮实际跑完：11 个版块 / 160 次开帖 / 145 帖真正打开 / 216 次滚动测量。**

### 已知的口径局限

1. **模拟器不是真机**，绝对值只在这台机器上有意义。
2. **基线轮跑的时候 Mac 上还有 agent 在跑 vitest/tsc**，会加噪声；A/B 那一轮是在所有 agent 空闲后跑的。
3. `adb shell input swipe` 不是真手指：事件点比真实触摸稀疏，所以每 move 的 JS 成本会被**低估**。

## 2. 指标的选择（以及我换掉了哪一个）

### 2.1 一开始用的：`dumpsys gfxinfo` 的 `Janky frames`

基线数据（n=145 次详情页滚动、9 次版块列表滚动）：

| 场景 | janky 帧 | 慢绘制帧 | p50 帧时长 | p95 | 最坏帧 | >100ms |
|---|---|---|---|---|---|---|
| 版块列表 慢拖 | **0.3%** | 0.3% | 18.4ms | 22.3 | 24.7 | 0 |
| 版块列表 快甩 | 0.6% | 0.6% | 18.1 | 21.9 | 24.2 | 0 |
| 帖子详情 慢拖 | **54.1%** | 47.1% | 18.3 | 22.1 | 36.6 | 0 |
| 帖子详情 快甩 | 36.2% | 22.2% | 18.4 | 21.8 | 52.1 | 0 |
| 帖子详情 横滑翻页 | 28.6% | 24.4% | 18.3 | 21.8 | 40.9 | 0 |

看起来是一个 180 倍的差距。

### 2.2 但同一张表里就藏着反例

**两个屏的帧时长统计上无法区分**：p50 18.3 vs 18.4ms，p95 22.1 vs 22.3ms。
一个指标说差 180 倍，另一个说完全一样——必须去看逐阶段分解。

### 2.3 逐阶段拆帧（`framestats` 按表头定位列）

同一套慢拖脚本：

| 阶段 | 版块列表 | 帖子详情 |
|---|---|---|
| 输入处理 | 0.01 ms | 0.01 ms |
| 动画 | 0.23 | 0.22 |
| 测量+布局 | 0.06 | **0.04** |
| 录制绘制指令 | 0.33 | **0.18** |
| 同步等待 | 0.18 | 0.30 |
| 下发绘制指令 | 0.96 | 1.02 |
| **交换缓冲（等 GPU/合成器）** | **13.36** | **13.61** |
| 总计（vsync→完成） | 18.37 | 18.21 |
| **系统排给这一帧的截止时间** | **33.33** | **33.33** |

三条结论：

1. **app 自己负责的每一段，两个屏都一样**（合计约 1.8ms）。
2. **13.4ms 全花在等 GPU 交换缓冲上**，这是模拟器 guest→host GL 管道的固定开销，改不掉。
3. **总时长 18ms 远小于 33ms 的截止时间**——按「错过 deadline」根本不该有 janky 帧。

所以 `Janky frames` 在这台模拟器上量的不是 app 的渲染成本。**§2.1 那张表作废。**

### 2.4 换成：app 每帧自己花的 CPU

`framestats` 里 `HandleInputStart → SwapBuffers` 之和（输入 + 动画 + 测量布局 +
录制 + 同步 + 下发），之后的交换缓冲不归 app 管。这个量对 app 侧改动是敏感的，
也是**真机上唯一会挤占 16.7ms 预算的那部分**。

## 3. 发现

### P0-1 冷启后开到第 4 个版块，之后全部变成「这个版块还没有主题」

**复现**（100%）：`force-stop` 后依次 deeplink 打开：
650 ✓ → 321 ✓ → 436 ✓ → 414 ✗ → 428 ✗ → 481 ✗ → 459 ✗ → 390 ✗ → 335 ✗ → 7 ✗。
再 force-stop，前 3 个又好了。同 app 内 WebView 打开 `thread.php?fid=650` 是登录态、内容完整。

**根因**（`net-empty-board.md` 有完整取证，并已用 vitest 端到端复现）——三处叠加：

| 位置 | 原行为 | 后果 |
|---|---|---|
| `core/net/envelope.ts:65` | 顶层既无 `data` 又无 `error` 时把**整个顶层当 data** | 任何陌生 JSON 都成了「合法的空主题列表」 |
| `core/api/topic-list.ts:323` | 只检查 `data` 是不是 record | 结构完全不对也算成功 |
| `core/net/strategies/format-rotation.ts:72` | **只要「能解析」就把组合记进 `comboCache`** | 坏组合被永久钉死 |

`comboCache` 在 `store/nga-client.ts:47` 的模块作用域，key 是接口粒度的 `'thread.php'`——
**版块列表 / 搜索 / 收藏夹 / 热帖 / 精华区 / 某人的主题共用同一条记录**，
所以一旦轮换到一个「能解析但没有 `__T`」的组合，这半个 app 一起失效，
而唯一复位手段是杀进程（版块页的「刷新」不会 `forgetSuccessfulCombo`，详情页有这个入口）。

**修复**：结构键校验 + 链内一票否决（坏组合根本进不了缓存）+ 缓存 10 分钟 TTL 自愈 +
版块页「刷新」先清组合缓存 + 空态文案分三档 + `__output=11`（全仓零 fixture 零单测的格式档）退出默认轮换。

**设备验证通过**：新包上连开 6 个版块，414 仍失败但**其后的 428 / 481 照常出内容**
（旧包一旦失败就全线失效），且 414 现在是**错误页而不是假空态**，带服务端信息
「服务端返回 HTTP 200 / 第三方客户端被拦是最常见的原因」+ 重试 / 用网页版打开 / 重新登录三个出路。

### P0-2 凭证只放 `Cookie` 头，会被 OkHttp 顶掉

`core/net/auth.ts:38` 把凭证拼成 `Cookie:` **请求头**。而 `expo/fetch` 在 Android 上用的是
RN 的 `OkHttpClientProvider` 单例，并挂了 `JavaNetCookieJar(ForwardingCookieHandler)`——
也就是 **WebView 的 `CookieManager`**。反编译 okhttp-4.12.0 的 `BridgeInterceptor`：
`Host` / `Accept-Encoding` / `User-Agent` 都有 `Request.header(...) == null` 守卫，
**唯独 `Cookie` 是无条件 `header()` 替换**。

只要 jar 里对该域名有任何 cookie，我们手写的 `Cookie: ngaPassportUid=…` 就被整条替换掉。

**设备上观察到的**：改前包打开帖子出现服务端原话「**1:未登录；[登录] [注册]**」，
改后包同一帖正常。**但改前包是间歇性失败**（4 次里第 1 次失败、第 2 次成功），
所以这是「与假说一致的观察」，不是受控证明——是否被顶取决于那一刻 jar 里有没有该域名的 cookie。

**修复**：新增 `AuthMode: 'both'` 并设为默认——Cookie 头 + form 字段一起带。
没有直接换成纯 `form`（MNGA 的做法）是因为那会一次性改掉所有接口的认证方式；
`'both'` 是严格更安全的一档。要不要收敛成纯 form，等真机验一轮再定。

**顺带修正一条 ADR**：`ADR-0002` 写的「每次重试前重建 HTTP client」在 RN 上是**空操作**——
`nga-client.ts:40` 的 `createTransport()` 只新建了一个 JS 闭包，底下的 `OkHttpClient`
是 `ExpoFetchModule` 里 `by lazy` 的模块级单例，连接池 / dispatcher / cookie jar 全共享。

### P1-4 图片回收串图（走查外发现，但是真缺陷）

`ui/bbcode/content-image.tsx` 的 `natural` / `failed` 是裸 state。FlashList 换一张图
复用同一个组件实例时，**新图会顶着上一张的宽高比、甚至上一张的「图片加载失败」画面**。
`Avatar` 的 `failed` 同样。已修：两个 state 都跟着地址一起记，地址对不上就当没量过。

### P1-5 版面镜像行的负数版块 ID 被当成无符号 32 位

走查中点「小窗视界 [版面镜像]」进去是错误页，服务端原话「**56:版面ID4286241377不存在**」。
`4286241377 = 2³² − 8725919`，即 **−8725919 的无符号 32 位表示**；NGA 的负数 fid 是特殊版块
（−7 网事杂谈、−8 某人的个人版面，个人版面 fid 形如 `-uid`）。
`core/api/topic-list.ts:78` 的 `parseShortcut` 直接拿 `sfid` 用了。

### P2 其它（已量到，未处理或按现状接受）

- **内存**：一个进程里连看 12 帖，PSS 172 → 271MB，**增长全在 Native Heap**（52 → 124MB），
  Java Heap 全程 14–26MB 且在降。Android 8+ 的位图分配在 native heap，15MB/帖 是位图量级
  ——**不是 Query 缓存**（20 帖的整页数据撑死几 MB，差两个数量级）。
  且**不是线性泄漏**：前 4 帖 +58MB，后 8 帖只 +14MB，涨到 ~124MB 封顶。
  静置 6 分钟不回落，系统 trim 只吐出 10MB。峰值 271MB 未越 300MB 红线。
  ⚠️ 这次把 `cachePolicy` 从 `disk` 改成了 `memory-disk`（`disk` 档不带内存缓存，
  回收后要重新读盘+解码），**内存只会更高**，真机上要重新量这条。
- **冷启动**：Activity 显示中位 260ms，首屏出内容中位 **2.4s**（5 次：2.50/2.35/2.42/2.41/2.37），
  非常稳定。这 2.4s 里含拉版块树的网络时间。
- **版块首屏**：中位 2.8s，p90 3.6s（n=10）。
- **主题打开**：145/147 个真实主题成功，中位 2.4s、p90 2.9s、max 7.1s。
  ⚠️ 走查脚本一度把**版面镜像行 / 合集行**（点开是另一个版块的主题列表，正确行为）
  和**活动帖跳系统浏览器**（`jumpUrl`，正确行为）算成了失败，我报过一个错误的
  「10% 打开失败率」——实际计入缺陷的只有 2 条（1.2%）。
- **列表续页正常**：连甩 14 轮，累计看到的不同主题从 7 线性涨到 130（每轮稳定 +9~10），
  无停滞。P0-1 的触发条件是**跨版块切换**，不是同版块内翻页。
- **快甩空白：指标不成立，已作废。** 我写了一个「正文区整行同色的像素行占比」的检测器，
  连续 6 次快甩中截图得到 10% → 42% → 42% → 44% → 31% → 25%，一度当成「高速甩动时接近半屏空白」。
  **但目视检查那张 44% 的截图，内容是完整渲染的，一个空缺都没有**——检测器数的是「整行同色」，
  而这个奶油底 + 大行距的排版里，文字行之间、卡片间距、内边距本来就是大片同色背景。
  静止画面测出来是 7.8%，和甩动中的 43% 确实有区分度，但两次停在不同的滚动位置、排版密度不同，
  无法排除这个混淆。**结论：这个检测器没有被验证能指示「内容缺失」，不作为缺陷依据。**
  要测 FlashList 的空白，正确做法是抓 `onBlankArea`（FlashList 自带的空白区回调）或录屏逐帧比对，
  不是靠像素同色率。
- **通知轮询** 前台常驻 60s 一发 `nuke.php`，已加「拉空退避」（60→120→180→300s）。
- **`staleTime` 全默认 0**：每次进屏都重新请求。详情页已按页加缓存；版块列表那条**故意没动**
  （怕把 P0-1 的验证挡住）。

## 4. 性能改动的验证结果：没有可测量的差异

三条修复线（详情页重渲染、渲染成本、网络可靠性）落地后，用 §2.4 的指标做**同一个帖子**的对拍
（改前包从 `git worktree` 在 HEAD 上重建，两包各跑 3 轮 × 360 帧）：

| 场景（app 每帧 CPU） | 改前 p50 / p95 / >8ms | 改后 p50 / p95 / >8ms |
|---|---|---|
| 版块列表·慢拖（对照组） | 3.03 / 7.18 / 2.2% | 2.82 / 6.97 / 2.5% |
| 帖子详情·慢拖 | 2.17 / 4.87 / 0.3% | 2.23 / 4.99 / 0.3% |
| 帖子详情·快甩 | 2.63 / 6.21 / 2.2% | 2.37 / 5.96 / 1.9% |
| 帖子详情·横滑翻页 | 1.87 / 7.58 / 4.9% | 2.34 / 8.84 / 6.8% |

**结论：慢拖持平，快甩略好，横滑略差，全部在噪声范围内。不能声称性能有改善。**

### 为什么没有收益——我前期分析里的两个错误

1. **`floorContext` 每次渲染新建这个机制确实存在，但在纯滚动场景下没被触发。**
   `onViewableItemsChanged` 只调 `recordReadFloor`，而 `recordReadFloor` 写的是
   `useHistoryStore`——**TopicScreen 并不订阅这个 store**，所以滚动过程中 TopicScreen
   根本不重渲染，也就没有可回收的重复渲染。
2. **我把 JS 线程的工作和 UI 线程的帧阶段混为一谈了。** New Arch 下 JS 线程的工作
   （同步 SQLite 写、PanResponder 回调）不直接计入 UI 线程的帧阶段，只有 commit 会跨过去。
   所以「把同步写盘搬出滚动热路径」「把手势搬到 UI 线程」这两条即便有效，
   也不会体现在我量的这个指标上。

### 那这些改动还该留着吗——该留，但理由不是「更快」

- **滚动热路径上的同步磁盘写**（`withTransactionSync` + `runSync`，慢拖时一秒十几次）
  客观上是浪费，节流到 1s 语义不变（只前进、退屏/退后台一定落盘）。
- **`renderItem` 内联箭头函数**会让 FlashList v2 的 `ViewHolder` memo 恒为 miss
  （`dist/recyclerview/ViewHolder.js:73` 比较 `prevProps.renderItem === nextProps.renderItem`），
  一旦将来 TopicScreen 真的在滚动中重渲染（加个进度条、加个悬浮按钮状态），
  代价会立刻显现。
- **`cachePolicy="disk"` 不带内存缓存**是事实，回收后重新解码是实打实的开销。
- **P1-4 的回收串图是可见缺陷**，跟性能无关。
- 手势改到 gesture-handler 消除了「纵向滚动时每个 move 都跑一段 JS 判定」——
  真机上手指的 move 事件比 `adb input swipe` 密得多，这条的收益在真机上才量得出来。

## 5. 要真正回答「手感够不够好」，还缺什么

这台模拟器每帧 13.4ms 花在 GL 管道上，app 的 2ms 淹没在里面。**必须去真机测**：

1. **真机跑同一套 `perf.py` / `ab.py`**（用户日常用 Android 真机验收）。真机上交换缓冲
   通常 2–4ms，app 的 2ms 才会真正参与 16.7ms 的预算竞争。
2. **JS 线程要单独量**。UI 线程帧阶段看不到 JS 侧的工作，而这次三条改动里有两条
   （节流写盘、手势上 UI 线程）作用在 JS 线程。建议用 Hermes sampling profiler 或
   `react-native-performance` 打点，而不是继续靠 gfxinfo 推断。
3. **FlashList 的空白区**要用 `onBlankArea` 回调或录屏逐帧比对来量，
   不能用我这次那个「像素同色率」检测器（§P2 已作废）。真机上高速甩动是最容易出白屏的场景，
   值得补一个可信的量法。
4. **首页 300+ 版块的分类页未实测**：`ui/board-icon.tsx` 的占位斜纹是 8 条带
   `backgroundColor` + `transform` 的绝对定位 `View`，按 RN 0.86 的摊平规则**每条都是真的
   Android View 且各带一个 stacking context**——一屏三十个没图标的版块就是 240 个视图节点。
   已 `memo`，但要根治得换方案（9-patch / 底纹图 / Skia），属于重构，建议单独立票。

## 6. 验收标准（用真机数据重新填）

| 指标 | 目标 | 依据 |
|---|---|---|
| app 每帧 CPU（真机） | p95 < 8ms | 留出一半 16.7ms 预算给合成与其它 |
| 滚动 janky 帧（真机） | ≤ 5% | Play Console「渲染缓慢」不良阈值 25%；做得好的 app 在 5% 以内 |
| 冻结帧（>700ms） | 0 | Android Vitals 阈值 0.1%（本轮模拟器上已是 0，>100ms 帧也是 0） |
| 版块可达性（冷启逐个开） | 11/11 | P0-1 已修，414 单独跟进 |
| 主题打开成功率 | ≥ 99% | 本轮 145/147 |

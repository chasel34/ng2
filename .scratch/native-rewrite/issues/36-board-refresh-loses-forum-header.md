# 36 — P2:版块页下拉刷新之后「版头 + 子版块」整块消失,重进也不恢复

**Status:** resolved

**Severity:** P2(功能可用,但刷新一次就永久少掉两块内容:置顶版头入口与子版块 chip 行,
连带「更多 → 子版块」变成空态「这个版块没有子版块」——子版块订阅/屏蔽这条路整条断掉,
除非杀进程重开)

## 现象

`emulator-5554`,`com.chasel.ng2.n` debug = HEAD c6c1e27,所有者账号已登录,
版块 **fid=-7「网事杂谈」**(合集/大区):

1. 深链或宫格进 fid=-7 → 列表顶上有「版头」分组;「更多 → 子版块」列得出 20+ 个子版块
   (网络游戏综合 / 游戏综合讨论 / 消费电子 IT新闻 / 篮球 / … 带「已订阅」「未知」「不可更改」三态)
2. 在列表顶部下拉刷新一次
3. 回到列表:**「版头」分组没了**,第一行直接是普通主题
4.「更多 → 子版块」:**空态「这个版块没有子版块」**
5. **退出这一屏再重进(甚至走 `am start` 深链重新进版块)照样是空的** —— 只有杀进程才恢复

第 5 步是这张票值得单开的原因:它不是「刷新那一下没画出来」,是**坏状态被留在了内存里**。

## 定位(未改代码)

两块内容同源,都挂在 `__F` 上,所以是一起消失的:

- `ui/board/BoardScreen.kt:132-134`
  `val headTid = firstPage?.board?.toppedTopicId`(`__F.topped_topic`)、
  `val subBoards = firstPage?.subBoards.orEmpty()`(`__F.sub_forums`);
  `:447-452` 两个 item 分别以 `headTid != null` / `subBoards.isNotEmpty()` 为条件。
- `ui/board/SubBoardsScreen.kt:87` 读的是**同一份** `state.pages.first().subBoards`,
  所以那一屏跟着变空。

坏状态留在内存的机制:`data/board/TopicListRepository.refresh(key)`(`:109-112`)
调 `fetchInto(key, page = 1, replace = true)`,`:154` 的
`val pages = if (replace) listOf(fetched) else state.pages + fetched`
把**整个 pages 换成刷新到的那一页**。这一页要是没有 `__F`,
之后 `ensureFirstPage` 看见 `pages` 非空就不再拉(`:87-95`),于是永远出不来。

## 是服务端不下发,还是解析丢了?——**没能坐实**,但两侧都做了排除

### 服务端侧(curl 对拍,游客态)

`POST https://bbs.nga.cn/thread.php?fid=<fid>&page=1&<format>`,
带 `X-User-Agent: Nga_Official` + 设备 WebView UA + `Referer: https://bbs.nga.cn/thread.php`:

| 请求 | 响应字节 | `__F` | `sub_forums` | `topped_topic` |
|---|---|---|---|---|
| fid=7 `__output=8` 第 1 次 | 15458 | ✅ | ✅ | ✅ |
| fid=7 `__output=8` 第 2 次 | 15458 | ✅ | ✅ | ✅ |
| fid=414 `__output=8` 第 1 次 | 40142 | ✅ | ✅ | ✅ |
| fid=414 `__output=8` 第 2 次 | 40142 | ✅ | ✅ | ✅ |
| fid=7 `__output=11` | 20399 | ✅ | ✅ | ✅ |
| fid=7 `lite=js` | 15535 | ✅ | ✅ | ✅ |

结论:**服务端不会「第二次就不下发 `__F`」**,三种格式也都带 `__F`
(而且都是 `data` 下的**具名键**,不是 `__output=11` 那种「真数组」位置量,
所以 `orderedEntries` 那条兼容路径不参与)。

**但现场那个 fid=-7 对不上这张表**:它是登录态才打得开的合集,
游客 curl 直接回 `{"error":{"0":"1:未登录", …}}`(403),复现不了。
用所有者的 cookie 去 curl 又越了走查纪律里「绝不打印/记录 cookie 值」的线,所以没做。

### 解析侧(读代码)

`core/api/TopicList.kt:296` 就是一句 `val forum = root["__F"] as? JsonObject`,
`:301` 是 `forum?.get("sub_forums") as? JsonObject`,**与格式无关、没有位置量、没有分支**。
清洗六步(`net/sanitize`)也不动 `__F`。单看代码找不到「解析会丢 `__F`」的路径。

### 还剩的两个嫌疑

1. **`thread.php` 的组合缓存是接口粒度共用一槽**(inventory §3 已列为已知风险:
   「`thread.php` 六个业务共用一槽」)。刷新那一发有没有可能拿到了别的业务
   (24h 热帖 / 搜索 / 某人的主题)喂进去的组合、打成了一个形状不同的请求?
   `rejectNonTopicList` 只否决「不是主题列表」,**一个没有 `__F` 的主题列表它是认的**。
2. **合集(fid < 0)在登录态下的 `__F` 行为**可能与普通版块不同。

## 怎么一次坐实(下一轮照这个做)

app 自己有现成的仪器 —— 实验室的「本次运行的组合」会把**最近若干个请求的
返回 data 键集**原样列出来,例如走查里抓到的初次加载那一发:

```
18:17:52 成功 thread.php?fid=-7&page=1 (1 次尝试) [format-rotation] json @ https://bbs.nga.cn
  → data{__CU,__GLOBAL,__ROWS,__T,__T__ROWS,__T__ROWS_PAGE,__R__ROWS_PAGE,__F} 37 条
```

**初次加载这一发是带 `__F` 的。** 所以只要:

1. 进 fid=-7 → 下拉刷新一次 → 立刻去「设置 → 高级 → 实验室与诊断 → 本次运行的组合」
2. 找到刷新那一发 `thread.php?fid=-7&page=1` 的 `data{…}` 键集

- 键集里**没有** `__F` → 服务端那一发就没给,app 只是把它照单全收了
  (那么修法是「`__F` 缺失时不要用新页覆盖掉旧页的 board/subBoards」,而不是去改解析);
- 键集里**有** `__F` → 解析或状态这一侧丢的,顺着 `parseTopicList` 往下查。

## 期望(不论上面哪一支)

**刷新不该把已经拿到的版块元信息弄丢。** `refresh` 用新页替换旧页时,
`board` / `subBoards` 这两项建议按「新的有就用新的,新的没有就留旧的」合并 ——
和分类树那边 `mergeBoardTree`「组成以服务端为准,单个字段服务端没给才回落缓存」
(`data/board/BoardTreeLoad.kt:63-73`)是同一条口径,现成的先例。

## 验收判据

1. [x] 进 fid=-7(或任一带版头/子版块的版块)→ 记下「版头」在不在、「更多 → 子版块」的条数 N;
2. [x] 下拉刷新一次 → 「版头」仍在、子版块仍是 N 条;
3. [x] 退出重进版块 → 同上;
4. [ ] 顺带把实验室组合表里刷新那一发的 `data{…}` 键集贴进本票,把上面那个二选一钉死。

(1–3 由 JVM 单测钉住 —— 见 Comments;4 需要设备 + 登录态,**待所有者**。)

## Comments

### 2026-08-23 修复:刷新不覆盖版块元信息

**没有去改解析,改的是状态合并**——票面「怎么一次坐实」的两支里,不管落在哪一支,
`refresh` 用新页整份替换旧页这一步都是错的:第一支(服务端那一发就没给 `__F`)要靠它兜住,
第二支(解析/链路丢了)同样要靠它兜住。而且这一支才是「退出重进也不恢复」的成因:
`fetchInto(replace = true)` 把 `pages` 换成刷新到的那一页,`ensureFirstPage` 看见
`pages` 非空就不再拉,坏状态一直留到进程重启。

`data/board/TopicListRepository.kt`:`fetchInto` 里 `replace = true` 的那一支改成
`keepBoardMeta(state.pages.firstOrNull(), fetched)`。口径**照抄** `BoardTreeLoad.mergeBoardTree`
的那一条(票面点名的先例):**新的有就用新的,新的没有才留旧的**。两层:

- 页级:`board` 整个缺席(`__F` 没来)→ 留旧的;`subBoards` 为空列表 → 留旧的;
- 字段级(`keepBoardFields`,照抄 `mergeBoard`):`info` / `iconUrl` / **`head`(版头)**
  服务端这次没给才用旧值。身份对不上(id/kind 不同)就整份用新的,不补齐 —— 那是
  另一个版块的元信息,补上去串味。

主题本身(`__T`)**不参与合并**,仍旧以刷新那一发为准;`retry` 也不受影响(它先
`put(key) { State(loading = true) }` 把整条 State 丢掉,`previous` 是 null,
「更狠的一档」的语义原样保留);翻下一页(`replace = false`)那条路一行没动。

### RN 版原行为

RN 侧**也是这个缺陷**,没有可照抄的保留语义:`store/topic-list.ts` 的
`useRefreshTopicList` 把 pages 砍到 1 再 `refetchQueries`,TanStack 用新的第一页整份替换,
`app/board/[id].tsx` 与 `app/board/sub-boards.tsx` 都直接读 `data.pages[0]`。
所以这是**已知缺陷不随迁**的一条(spec §一.5 口径),按票面「期望」修掉并记在这里。

### 有意偏离 / 决定

- **子版块只按「整块为空」回落,不做逐条合并**。服务端真把某个子版块下线时会连着新的
  `sub_forums` 一起下发,那一份非空,新的赢;只有整块空才回落。空 `sub_forums:{}`
  与「`__F` 没来」在这一层同形,分不开——分不开时选「留旧的」:子版块下线是罕事,
  `__F` 缺席是本票的现场。
- **`head` 做字段级回落**(而不是只在 `board` 整个缺席时保留)。`topped_topic` 为 0/空串
  时解析成 null,与「`__F` 没给这个字段」在这一层同形;不这么做的话「`__F` 来了但没带
  `topped_topic`」仍然会让版头消失,症状和本票一模一样。代价是版头真被撤下时会粘到
  进程重启——与分类树那边 `info`/`iconUrl` 的取舍是同一笔账。

## 撤回(2026-08-23,票 18 D 段续,HEAD e7142e8)

**这是个假缺陷,「版头 + 子版块消失」根本没发生过 —— 我当时只是没滚到列表顶部。**

复现尝试(登录态,`am force-stop` 冷启后深链进 fid=-7,列表只有第 1 页、天然在顶部):

| 步骤 | 「版头」 | 子版块 chip 行 | 「更多 → 子版块」 |
|---|---|---|---|
| 刚进屏 | ✅ 在(y=306) | ✅ 在(网络游戏综合 / 游戏综合讨论 / 手机 网页游戏综合讨论 / …) | ✅ 31 个节点,三态齐 |
| 一次真的下拉刷新之后 | ✅ 还在(y=306,位置一模一样) | ✅ 还在 | ✅ 还在 |

**原始现象是怎么来的**:两个观察错误叠在一起。

1. **「版头没了」= 列表不在顶部。** 当时先跑了 `scan_sub.py`(连划 14 屏,顺带把第 2/3/4 页
   都加载了进来),再用**两次** `input swipe 540 500 540 2100` 想滚回顶部 —— 每次约 1600px,
   而那时列表里已经有 140 条主题、三万多像素,两次远远不够。屏幕上于是是「一条主题被切了一半
   顶在最上面」,和「版头不见了」长得**完全一样**。后来补拍的截图坐实了这一点:
   顶栏底下直接是半行主题,列表明显在中段。
2. **「下拉刷新」那一下其实没发出请求。** 事后翻实验室「本次运行的组合」的
   【最近 11 个请求】,那段时间只有 `thread.php?fid=-7&page=1/2/3/4` 四发(page=1 是进屏那一发,
   2/3/4 是 scan 的无限滚动),**刷新之后再没有第二发 page=1**。列表不在顶部,
   `PullToRefreshBox` 根本不响应,所以「刷新前后」比较的是同一份数据。

「更多 → 子版块」那次空态也跟着解释掉了:`SubBoardsScreen` 读的是同一份
`state.pages.first().subBoards`,页数据从头到尾没换过,当时应该也不是空的;
两次都是在同一个错误现场里连着看的,没有独立证据。**不留任何未解释的残留。**

### 留下的口径(这才是这张票的价值)

- **「不在顶部」和「顶部那一项没渲染」在 uiautomator 里长得一模一样。**
  判断列表头部时,先断言**列表确实在顶部**(最靠上的那个内容节点的 `bounds` 上边缘
  应当紧贴顶栏,而不是被切一半),再谈「某个 header 在不在」。
- **`input swipe` 回顶要按已加载的页数算次数**,一次约 1600px;翻过 N 页之后想回顶,
  更可靠的做法是 `am force-stop` 冷启重进(顺便得到一份干净的、只有第 1 页的状态)。
- **「下拉刷新到底发没发出去」有现成的仪器**:实验室「本次运行的组合」的
  【最近 N 个请求】里该多一发 `thread.php?fid=…&page=1`。别靠「列表看起来变了」判断 ——
  列表本来就一直在变。

**主控裁定(2026-08-23)**:原始现象判为假缺陷(见上「撤回」),但 fix 里 `keepBoardMeta` 的刷新保留语义与 `mergeBoardTree` 口径一致、有 8 条单测、且修掉了 RN `store/topic-list.ts` 同款已知缺陷——**保留修复**,票按 resolved 收。

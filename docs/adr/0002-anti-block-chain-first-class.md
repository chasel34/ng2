# 反封锁链是网络层的一等公民,第一天就进架构

NGA 会针对性封禁第三方客户端(表现为 XML/JSON 接口解析失败)。core 层的 fetcher 从 M1 起就是策略链而非裸 fetch:格式参数交替(`lite=xml` ↔ `__output=10` ↔ JSON,成功组合按 key 缓存)→ 换账号重试(取下一个已登录账号 cookie)→ Web 反解(read.php 专用,从网页内联 JS 反解)→ 帖子缓存 → 网页兜底页。UA 策略:默认 `X-User-Agent: Nga_Official` 辅助头 + 系统 WebView UA(NGA-CLIENT v4 验证的做法),`read.php` 可切 Windows Phone UA。附件图片域名从 `read.php` 响应的 `_ATTACH_BASE_VIEW` 动态获取,禁止硬编码。

不做自建反向代理(需要长期维护服务器,个人使用不值)。

附带纪律(Expo SDK 57 Android `expo/fetch` 乱序 bug,expo/expo#47762):fetcher 禁止 clone/tee response,一律一次性 `.text()` 读取。

## 现状修正(2026-08-13,「冷启动后所有版块都空」排查)

排查过程与取证见 `.scratch/perf-2026-08/net-empty-board.md`。四条与本 ADR 直接相关的更正:

1. **「成功」的判据不能只是「洗得成 JSON」。**
   链原本认为「能解析 = 这个组合是好的」,于是一个**能解析但根本不是该接口响应**的东西
   会被当成结果交给调用方,并被 `format-rotation` 记进成功组合缓存钉死。
   现在调用方可以给出一票否决(`NgaRequest.validate`),形状不对按 `kind:'parse'` 继续轮换;
   `thread.php` 的判据是「`__T`/`__F`/`__ROWS` 至少有一个」(空版块也带这些键)。
   同理 `parseNgaJson` 默认要求顶层有 `data`/`error` 壳,顶层即 data 的接口显式声明 `bare`。

2. **成功组合缓存必须能自愈。** 原本只有「全组合都失败」一条出口,组合半通不通时永远走不到,
   唯一复位手段是杀进程。现在条目有 10 分钟保质期(`DEFAULT_COMBO_TTL_MS`),
   缓存里那个组合当场失手也会立刻摘掉。
   ⚠️ 缓存 key 是**接口粒度**(`thread.php`),即版块列表 / 搜索 / 收藏夹 / 热帖 / 精华区 /
   某人的主题**共用一条记录**——这是有意的(被封的粒度确实是接口),代价是一条记录坏掉
   会让这半个 app 一起失效,所以自愈与可观测性是它的配套条件,不是可选项。

3. **`renewTransport`(「每次重试前重建 HTTP client」)在 RN 上是空操作。**
   `createFetchTransport(expoFetch)` 只是新建一个 JS 闭包,底下的 `OkHttpClient` 是
   `ExpoFetchModule` 里 `by lazy` 的**模块级单例**(`NativeRequest` 里的
   `client.newBuilder().build()` 同样共享连接池 / dispatcher / cookie jar)。
   这一档的实际效果只有「换一次组合」,**不要以为重试换了新连接**。真要换连接得走原生模块。

4. **凭证不能只放 `Cookie` 请求头。** okhttp 的 `BridgeInterceptor` 对 `Cookie`
   是无条件 `header()` 覆盖(`Host`/`UA`/`Accept-Encoding` 才有「已有就不覆盖」的守卫),
   而 `expo/fetch` 挂的 cookie jar 就是 WebView 的 `CookieManager`。
   换到镜像域名后 jar 里没有 passport cookie,NGA 一下发自己的 cookie 就把我们的头顶掉,
   请求**静默变成游客**。默认认证档位因此改成 `both`(Cookie 头 + form 字段,form 不过 cookie jar)。

5. **可观测性是这条链的一部分。** 成功也要留记录(用了哪个组合、`data` 顶层有哪些键、几条数据),
   否则「链自认为成功、拿回来的却是空数据」在日志里一个字都不会出现。
   记录只含结构信息与 uid,**绝不含 cid 与正文**。

## 现状修正(2026-08-13/14,「一打开就是未登录错误页」排查)

排查与真机取证见 `.scratch/perf-2026-08/device-report.md` §3。这一条是上面第 4 条的直接延伸。

6. **「未登录」是传输层错误,不是语义错误——它决定错误可不可重试。**
   `defaultRetryable` 原本把 `kind:'server'` 一律判成不可重试,理由是「服务端说找不到这条数据,
   换几次策略还是这个结果」。这对**语义**错误成立,但服务端说「未登录」讲的不是
   「你要的这条数据有问题」,而是「**这一发请求没被认出身份**」——上面第 4 条已经写明,
   身份能不能带上是**和域名强相关**的(cookie jar 按域名存),所以换个组合往往就好了。

   判成不可重试的代价是三重的,缺一不可才凑成那个 P0:
   - `runStrategyChain` 当场 `throw`,**链上后面的网页兜底和帖子缓存一个都轮不到**
     ——而网页兜底恰恰能拿到这一页(真机实测:同一个帖子接口报未登录,
     点「用网页版打开」正文完整渲染)。
   - `format-rotation` 里「能解析出服务端语义错误 = 这个组合是通的」那条规则会把
     **丢身份的那个组合记进缓存**,于是该接口被钉死在那个域名上,后面每一次请求都错。
   - 用户看到的是一整页错误,连点「重试」也没用。

   现在判据集中在 `AUTH_LEVEL_SERVER_MESSAGES`(`errors.ts:isAuthLevelServerError`),
   命中就标 `retryable: true`,顺带避开上面那条缓存规则。**游客态也标可重试**——
   不是为了换域名(游客哪个域名都没 cookie,那一层在 `format-rotation` 里单独刹住),
   而是为了别把整条链掐死,让网页兜底/帖子缓存接手。

   **写操作(签到/点赞/回帖)走这条路也安全**:服务端回「未登录」就是它**拒绝**了这一发,
   没有副作用可言,换条路重发才是用户要的结果。

7. **判据要按「这条错误在说什么」分类,而不是按 `kind` 一刀切。**
   上一条的普遍形式:`kind` 描述的是**错误从哪一层解析出来的**(传输 / 解析 / 服务端),
   而「要不要重试」取决于**服务端到底在说什么**。两者不是一回事,以后再往
   `FAKE_ERROR_MESSAGES` / `AUTH_LEVEL_SERVER_MESSAGES` 这类白名单里加词条时,
   问的应该是「换个组合有没有可能改变这个结果」。

## 现状修正(2026-08-14,「414 版块永远打不开」排查)

排查与取证见 `.scratch/perf-2026-08/device-report.md` §7。

8. **轮换档位的价值在于「它们不共用同一段服务端代码」,同源的两档凑不出冗余。**
   默认轮换表原本是 `['json', 'jsonLite']`,看着是两档,实际 `__output=8` 与 `lite=js`
   是**同一份字节**,后者只多包一层 `window.script_muti_get_var_store=`。
   NGA 给 `fid=414` 的那份响应里混进了声明 GBK 却是 UTF-8 的字节(还有 GBK/GB18030
   都解不出的字节),于是两档一起解析失败,**换遍 5 个域名拿回来的还是同样的坏字节**,
   这个版块在 app 里永远打不开。真正救得了的是 `__output=11`——它是另一个序列化器。

   所以往轮换表里加档位时,问的不该是「这又是一种格式吗」,而是
   **「它和表里已有的档位会不会一起坏」**。同理,`DEFAULT_MAX_ATTEMPTS` 要同时够
   「第一个域名试满所有格式」(坏字节靠换格式救)和「够得着后面几个域名」(被封靠换域名救),
   两个方向都不能为对方让路。

9. **「没验证过的档位不该进默认轮换」这条纪律是对的,但它的出口是「去抓样本」。**
   `jsonVerbose` 2026-08-13 因为没有真实样本被拿掉,注释里留了
   「抓到 fixture 再放回来」——2026-08-14 抓到了,也就放回来了,
   两份样本(可用的 `__output=11` 和**坏的** `__output=8`)都存进了 `api/__fixtures__`。
   坏样本要**故意留着**:它是「为什么必须有第三档」的唯一证据。

10. **同一类偏差会在不同地方复发:`isRecord` 按约定把数组排除在外。**
    `errors.ts` 认 `error` 的数组形态时踩过一次(§现状修正 2026-08-13),
    `api/fields.ts` 的 `orderedEntries` 又踩了一次——`__output=11` 的 `__T` 是
    **货真价实的 JSON 数组**,而 §0.6 说的「用字符串数字键当数组」只是 `__output=8` 的习惯。
    不认数组的后果是整页主题**静默变成 0 条**,比抛错难查得多。
    以后凡是遍历 NGA 下发的「列表」,都要同时接受对象形态与数组形态。
